# Decision log — project access groups + Login with Google

Date: 2026-06-12. Branch: `feature/access-groups-and-google-login` (corpo-valley-main + corpo-valley-chart).
Scope: (1) user-managed groups + per-project site/repo read/write/admin grants, (2) admin-configurable
Google Workspace login, (3) fixes for bugs found during the access-control review.

Product options were generated by a PM review against the platform vision (self-hosted single-org
"vibe-coding" platform; admin provisions identity, members self-serve everything after that; secure
posture is the default; must scale to hundreds–thousands of members). Each decision below records the
two options considered and why one won.

## D1 — Group governance: self-serve (chosen) vs admin-curated

Any member can create groups; the creator owns membership; platform admins can manage/delete any group.
Admin-curated groups would turn every team formation into an admin ticket — the exact bottleneck the
platform exists to remove. Risk is cosmetic (misleading group names), mitigated by showing owner +
member count wherever a group is pickable. Groups live in portal Postgres (`groups`, `group_members`),
not Keto: grants are resolved by the portal at request time, the data is relational (listing, counts,
joins), and Keto stays the platform-role authority only.

## D2 — Site permission standard: trusted edge headers (chosen) vs per-request permission API

The deployed-site permission contract for project developers is **three request headers**, injected at
the ingress edge after an auth subrequest to the portal:

- `X-CV-User-Id` — Kratos identity UUID of the visitor
- `X-CV-User-Email` — visitor email
- `X-CV-Perm` — `read` | `write` | `admin`

Visitors without `read` never reach the app (401 → login redirect for anonymous; 403 for signed-in
non-readers). An app with zero auth code is still fully protected. The alternative (every project
calls a portal permission API per request) makes each project — and each AI agent editing one —
responsible for getting authz right, multiplies latency, and breaks the "authorization is built in"
template promise.

Why the headers are trustworthy:
- ingress-nginx `auth-response-headers` always overwrites the listed headers from the auth-subrequest
  response, so a client-supplied `X-CV-Perm` never survives the edge;
- in-cluster bypass is blocked by the tenant egress baseline (`k8s.ts` tenantEgressPolicyObject):
  tenant pods can only egress to their own namespace, kube-dns, Kratos:4433, and the public internet —
  they cannot reach another project's Services directly. Same-namespace traffic can spoof headers, but
  a project's own containers are already one trust domain.

Enforcement endpoint: `GET /access/site/:slug` on the portal (no portal session middleware; validates
the forwarded Kratos cookie itself, short in-memory caches keep the per-request subrequest cheap).
`X-CV-Perm: admin` is an **in-app** permission class for project developers to use; it does NOT grant
portal-level project management (settings/secrets/delete stay owner-only).

## D3 — Legacy private/shared composition: replace with default-access dials (chosen) vs keep as a tier

`service_access`/`repo_access` are replaced by two per-project "default access for all signed-in
members" dials — `site_default_access` and `repo_default_access`, each `none | read | write` — shown in
the same UI as the grants table. Effective permission = max(default, direct user grants, group grants);
the owner is always `admin`. One mental model instead of two, and strictly more expressive (read-only
sharing was impossible before).

Write-preserving migration (matches the repo's own `open`→`shared` precedent, and is idempotent —
the new columns start NULL and are derived lazily from the legacy values until first written):
- site: `private` → `none`; `shared` → `write` (a shared site today lets any member fully use the app —
  mapping to `read` would break every existing shared project the day templates honor `X-CV-Perm`)
- repo: `private-edit` → `none`; `shared-edit` → `write` (literally its current advertised semantic)
The legacy columns are kept in sync on write for rollback safety but nothing reads them anymore.
New projects default to `none`/`none` (private), preserving secure-by-default.

## D4 — Google login visibility: Google-only with break-glass (chosen) vs side-by-side

When `auth.google.enabled` is on, the login page shows only "Continue with Google" (the requirement
says *instead of* password/code). Lockout safety: `/login?method=password` always renders the full
password/code form (linked discreetly as "Sign in another way"), admin recovery links keep working, and
the chart README tells the enabling admin to verify the fallback first. Existing password users who
arrive via Google are NOT auto-linked by email — Kratos creates account linkage only via matching
identifier; see Edge cases below.

## D5 — Google signup provisioning: auto-provision full members (chosen) vs pending approval

Requirement: "allow anyone from their google workspace domain to signup/login." A Kratos
after-registration (oidc) webhook calls the portal, which re-fetches the canonical identity from the
Kratos admin API and runs the same idempotent `ensureProvisioned` the admin flow uses (.bot identity +
Gitea accounts). The webhook needs no shared secret: it only names an identity id, and the portal
verifies everything against Kratos itself — a forged call can at worst trigger idempotent provisioning
of a real identity. Belt-and-braces: the dashboard lazily re-runs provisioning on first sight of an
unprovisioned session (this also makes the previously-stale comment in `routes/internal.ts` true again).
Under D3, a fresh signup has zero access to anything beyond what defaults/grants give — membership is
cheap. Domain restriction is enforced **inside Kratos** by the OIDC data-mapper (jsonnet `error` when
the `hd` claim isn't in `auth.google.allowedDomains` or `email_verified` is false), so it can't be
bypassed by talking to Kratos directly.

## D6 — Google client config surface: chart values + sealed secret (chosen) vs portal admin UI toggle

Kratos OIDC providers are static config; a portal-DB toggle can't reconfigure Kratos at runtime without
a restart anyway. So: `auth.google.{enabled, allowedDomains}` in chart values (admin-owned deployment
config), client id/secret in a new sealed secret `kratos-google-oidc` mounted as a second Kratos config
file (`kratos serve --config kratos.yaml --config google-oidc.yaml` — koanf merges them; this avoids
both secret-in-ConfigMap and the fragile whole-array env-var override). `generate-secrets.sh
--google-client-id/--google-client-secret` emits it. The portal learns the state via
`GOOGLE_LOGIN_ENABLED` env.

## D7 — Registration flow hardening

Enabling Google signup requires enabling the Kratos registration *flow*, which would also open
password/code self-signup via direct Kratos API calls (the portal UI never offered them). Mitigation:
`can_interrupt: true` web_hooks on `registration.after.password` and `registration.after.code` pointing
at portal `/internal/hooks/registration/deny`, which always rejects with a user-readable message. OIDC
is the only registration method that completes. Single-step registration is pinned
(`enable_legacy_one_step: true`) so the method set is deterministic.

## Gitea sync model (feature 1.2)

Repo grants map directly to Gitea collaborator permissions (`read`/`write`/`admin`); repo visibility
maps from the repo default (`none` → private repo; `read`/`write` → org-visible repo). A reconciler
(`services/repo-access.ts`) computes the full desired collaborator set (direct grants + group grants
expanded to members + default-`write` fan-out to all identities) and converges Gitea to it. **The portal
is the source of truth**: collaborators added by hand in Gitea's UI are removed on the next reconcile
(uniformity over side-channels — this is deliberate). Reconcile triggers: grant add/remove, default
change, group membership change (all projects granted to that group), project provisioning, and new-user
provisioning (default-`write` fan-out). The owner and `cvportal` are never touched.

## Bugs found and fixed on this branch

1. **(pre-existing, from audit)** Chart trusts `claude-code-mcp` for consent while the app's MCP
   deny-list *defaults to* the trusted list — so under chart values the platform `/mcp` endpoint 403s
   the very client the chart comment says drives MCP. Fixed: new `mcp.denyClientIds` value (default
   `argocd,gitea`) wired explicitly as `MCP_DENY_CLIENT_IDS` to **both** portal and mcp-gateway, with
   the code comment corrected.
2. **(pre-existing, from audit)** mcp-gateway Deployment received neither `TRUSTED_CLIENT_IDS` nor
   `MCP_DENY_CLIENT_IDS`, so its deny-list silently drifted from the portal's ("can't drift" by design,
   but only per-process). Fixed by the same explicit wiring.
3. **(pre-existing, from audit)** `mcp.enforceAudience: false` is the deployed default while the code
   calls it a transitional escape hatch. NOT flipped — common MCP clients still send empty `aud`, and
   the non-bypassable backstop (foreign-resource tokens always rejected) plus the gateway ownership
   check remain. Documented properly in values.yaml instead.
4. **service_access change was a DB-only write**: the deployed site's access never actually changed
   (the ingress only ever checked "any valid session", and `CV_SHARED` is baked at deploy time). Fixed
   structurally: the new `/access/site/:slug` endpoint reads the DB live on every request, so default
   and grant changes take effect immediately, with no redeploy.
5. **repo_access change never synced to Gitea**: switching private-edit ↔ shared-edit updated the DB row
   only; repo visibility stayed at creation-time value. Fixed by `syncRepoAccess` on every change.
6. **shared-edit never actually granted write**: repos were made public (clone-only) and no collaborators
   were ever added, so "any member can push" was fiction. Fixed by the default-`write` collaborator
   fan-out.
7. **Repo visibility was keyed to the wrong axis**: `provisionProject.ts` set the Gitea repo private flag
   from `service_access` (site!) instead of `repo_access` — a "custom" project with shared site +
   private repo got a **publicly readable repo**. Fixed: visibility derives from the repo default.
8. **Stale comment in `routes/internal.ts`** claimed lazy provisioning on first authenticated request
   existed in `middleware/session.ts`; it didn't (admin-create was the only path). The lazy path now
   actually exists (dashboard GET /), and the comment matches reality.
9. **Found during implementation:** the `cv-portal-ingress` NetworkPolicy didn't admit traffic from
   the `cv-ory` namespace, so the new Kratos registration webhook would have been silently blocked
   (Kratos fire-and-forgets it with `response.ignore`, making the failure invisible — only the lazy
   backstop would have saved signups). Chart netpol updated to admit cv-ory → portal:3000.

## Edge cases / known limitations (deliberate, documented)

- **Existing projects keep the old Kratos-whoami ingress** until their manifests are next regenerated
  (any access-settings save or capability change re-commits `k8s/ingress.yaml` with the new auth-url).
  Until then their site enforcement remains "any signed-in member" (the pre-existing behavior). The VAP
  accepts both old and new auth-urls, so neither generation is blocked.
- **Google signups have no `preferred_username`**, so Gitea/bot provisioning derives one from the email
  local part (existing `deriveBotUsername` convention). Collisions or reserved names are refused, and
  the user works fine portal-side; an admin can set a username later.
- **Existing password account + Google login with the same email**: Kratos will refuse the OIDC signup
  with a duplicate-identifier error (no silent account takeover). The user keeps using
  `/login?method=password`, or an admin can delete/migrate the identity. Automatic secure linking
  requires Kratos account-linking config that is out of scope here.
- **Default-`write` repo fan-out is O(members × default-write projects)** Gitea calls at reconcile time;
  fine at hundreds of users, revisit (Gitea org teams) at thousands.
- **Grant subjects store a denormalized Gitea username** captured at grant/membership time; admin
  username changes won't retro-update collaborator rows until the next reconcile of that project.
- **`X-CV-Perm: admin` vs portal ownership**: site `admin` is an app-level class only. Portal project
  management stays strictly owner-only (unchanged), including for users with `admin` grants.
- **CV_SHARED is unchanged**: it still controls the template database's per-user vs shared *data* model
  and is still baked at manifest-generation time. It is now orthogonal to access control (which is live).
- **Deny web_hooks rely on Kratos can_interrupt semantics** (registration aborts when an after-method
  hook returns 4xx). Verified against Kratos v1.3 docs; if a Kratos upgrade ever changes this, the
  fallback control is that portal UI/templates never offer password/code signup.
